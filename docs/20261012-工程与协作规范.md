# 工程与协作规范

创建日期：2026-10-12  
适用范围：`prototype/`

## 1. 唯一主线

- `prototype/` 是唯一活跃应用。新功能、修复、迁移、测试和部署配置都以此为目标。
- 不在根目录、`archive/` 或临时导出目录再建同源应用。
- 从历史实验复用内容时，先明确需求和文件差异，再只迁入必要部分。
- `dist/`、`.next/`、`.vinext/`、`.wrangler/` 和 `.sites-runtime/` 是生成或本地状态，不是源码入口。

## 2. 模块边界

| 区域 | 负责内容 | 变更要求 |
| --- | --- | --- |
| `app/` | 页面壳、App Router、API routes | 产品功能任务才修改，API 变更需同步验证数据一致性 |
| `public/` | 原型脚本、样式、图片与音频 | 不把工程配置或服务端逻辑放进来 |
| `db/` | 数据 schema 与数据库入口 | schema 变更必须伴随 migration |
| `drizzle/` | SQL migrations 与元数据 | 已应用的 migration 不回写，以新 migration 演进 |
| `lib/` | 可复用的服务端/平台支持 | 不堆放页面特有逻辑 |
| `build/` | Vinext、Cloudflare 与连接器构建支持 | 视为平台基础设施，修改后必须完整 build |
| `scripts/` | 安装、环境、构建脚本 | 保持非交互、可重复执行，异常时返回非 0 |
| `docs/` | 工程决策和运行说明 | 新建文档使用 `YYYYMMDD-` 前缀 |

## 3. 环境变量与敏感信息

1. 变量名、用途、是否必填和安全示例统一登记在 `.env.example`。
2. 本地真实值使用 `.env.local`；线上真实值使用托管平台 Secret。不在文档、源码或示例文件中提交密钥。
3. D1、R2 和 Service binding 通过托管配置声明，不伪装成 URL 环境变量。
4. 客户端变量等同于公开数据。密钥永远不使用 `NEXT_PUBLIC_` 前缀。
5. 新增变量时，同一个变更必须更新 `.env.example` 和 `README.md`。

## 4. 数据库变更

1. 修改 `db/schema.ts`。
2. 执行 `npm run db:generate`，审阅新 SQL，不盲目信任生成结果。
3. 先在本地 D1 验证 migration 和相关 API，再安排远程迁移。
4. 远程迁移前确认数据库目标、备份/回退方案和发布窗口；不把远程迁移隐藏在普通 build 脚本里。

## 5. 质量门禁

本地和 CI 统一入口：

```bash
npm ci
npm run check
```

`npm run check` 按以下顺序失败即停：

1. `npm run lint`：ESLint 静态规则。
2. `npm run typecheck`：TypeScript 无输出检查。
3. `npm test`：Node 原生测试入口。
4. `npm run build`：生产构建与路由生成。

当前尚无自动化测试，`npm test` 会明确报告 0 个用例，不得把这解读为业务已有测试保障。后续优先为以下部分建立用例：

- 计时器的后台、刷新和休眠恢复。
- 座位原子占用、心跳过期、释放和多标签页冲突。
- `human` / `npc` 数据口径分离。
- D1 migration 的前向兼容性。

基线中已存在的 lint warning 应登记并逐步清理；新变更不应增加 warning。

## 6. 任务分工与合并检查

- 任务描述要列明可修改边界；多人同时工作时，按目录或模块分配所有权。
- 共享文件（尤其是 `package.json`、schema、路由和公共样式）在修改前先确认是否有并行任务。
- 工程整理不顺带重构业务逻辑；业务功能不顺带复制新应用。
- 提交前检查改动文件列表，确认未包含生成产物、本地数据库、密钥、缓存或无关素材。
- 交付说明至少包含：改了什么、如何运行、如何检查、已知限制和下一步。

## 7. 发布前最小验收

- `npm run check` 通过。
- 托管平台上的 `DB` binding 存在，且目标库已应用必要 migration。
- 首页可打开，静态资源无成片 404。
- 房间状态 API 可读，占座、心跳、切换和释放的主路径可用。
- 浏览器控制台和 Worker 日志没有新增的阻断性错误。
